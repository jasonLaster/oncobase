# Public features page

`/features` is the public, indexable page for people deciding whether to use Oncobase and for agents that want to build on it. It uses the wiki's own palette (indigo `#4f46e5` in light and `#818cf8` in dark, neutral grays, navy in dark mode) with `.lp-oncobase` as a subtle tint, never a second brand color, so it matches the reader and the landing page. It reads as a marketing page first: each area leads with a visual or an interactive demo, then a short list, with tables only where a table is the clearest form. `/compare` (`specs/compare-page.md`) is its sibling for people choosing between tools.

## Routing and access

- Signed-out visitors can open `/features` with no redirect (`PUBLIC_PAGES` in `server/app-shell.ts`). It renders without a wiki session or database (`rootRouteFor` returns `features`).
- Unlike the landing and sign-in pages it is **indexable**: the server injects a canonical URL and no `noindex`, and `robots.txt` allows `/features` on the default site. Its share card ("Everything Oncobase can do") comes from `featuresRouteMetadata()` and is also served to link-preview bots.
- `/llms.txt`, `/features.md`, and `/compare.md` are static public files generated by `bun scripts/build-llms-txt.ts`, and `features-data.test.ts` and `compare-data.test.ts` fail when they drift. `features.md` is the markdown twin of this page (same section headings and introductions, every feature, the details, and the interface tables). `.md` URLs are wiki-page aliases behind the gate, so the server exempts exactly `/features.md` and `/compare.md` and never a pattern.
- Never name a `public/` folder after a route: `public/features/` once made the standalone server read a directory and return 500. The server now only treats files as files, and the images live in `public/feature-shots/`.

## One source of truth

`src/pages/features-data.ts` holds the areas (Read, Ask, Protect, See the data, Collaborate, Speed, Build), every feature (name, one sentence, where it lives, and the API/CLI interface when it has one), the interface table for agents grouped into four categories, the grouped "details" list, the section copy, and the hero lede. The page, the full table, the interface and detail accordions, and the three text files all render from it. Add a feature there and run the generator.

## Header

The shared header (`PublicChrome.tsx`, also used by `/compare`) has the Oncobase brand, the in-page section links, the theme toggle, and a GitHub button. It shows which section is in view (scroll-spy, `aria-current="location"`, an underline) and on phones keeps a sideways-scrolling link row with the current one scrolled into view. There is no sidebar.

## Sections

1. **Hero.** "Everything Oncobase can do." A real screenshot with three numbered pins (page tree, smart tables, outline) and a map of the areas.
2. **Read.** The file palette, an interactive table demo (real table component, sample-data and width buttons, lazy-loaded), the phone reader, a call-transcript demo (Overview, Formatted, and Raw pages using the real note-bundle navigation, with timestamps that jump into the raw transcript), a Mermaid diagram demo (the real renderer), illustrations in light and dark with a draggable compare handle on the image, and six cards.
3. **Ask.** A chat conversation showing the agent's steps and citations, a four-step flow of how it finds context, AI search, and a table of which tool to use when.
4. **Protect.** A five-layer flow, the interactive role and redaction demos, six cards, and the rules agents follow for redaction.
5. **See the data.** Diagnostics timeline and imaging viewer cards (reusing the landing images), plus cards for comparison, pathology, annotations on scans and slides, touch, lab import, and previews.
6. **Collaborate.** An interactive comments demo: an inline highlighted passage with the comment pane on the right (resolve, react, reply, view all threads), recreated with fictional people because real comments run on Liveblocks and can't be captured with sample threads.
7. **Speed.** A three-speeds flow (pages you've opened, pages you haven't, the first visit), a stat strip (about 230 ms to first paint, 0 requests to reopen a page, 20 ms for a folder of 500 pages, measured in a controlled test), and a checklist of the techniques behind them.
8. **Details.** "Built with attention to detail", dialed back to a short list of plain items in four collapsed groups (Reading; Speed and connection; Search, sharing, and publishing; Safe and accessible). Each group header, preview line, and count stays visible.
9. **Build.** "Have your agent build your own knowledge base." Two cards (build with Oncobase, or have your agent borrow from it, MIT), the publish loop, starter commands, and the interface table collapsed into four categories (Pages, files, and downloads; Search, chat, and agent tools; Clinical data; Publish and build).
10. **The full list**, a closing call to action (GitHub, Diana's knowledge base, how it compares), and a one-row footer with the osteosarc.com credit and the CC BY credit for the MRI image.

## Accuracy rules

Claims come from the code, checked in October 2026. Do **not** claim: sorting, filtering, or search inside tables; an MCP server; automatic dark-theme swapping of `data-theme-pair` images in the reader (only the `-light` file shows there; the landing, sign-in, and this page choose the matching file themselves); table column widths beyond the session; or that link previews are re-redacted. The redaction skills that spell out what to hide live in Diana's vault, not in this repository; the CLI ships only `wiki-quickstart` and `check`. The comments demo is a recreation, and says so.
